1. INTRODUCTION
================================================================================

  Name        : slicer
  Command     : slice
  Helper      : spec
  Version     : 0.1.0
  Language    : Python 3.10+
  Platform    : Windows / Linux / macOS / Termux
  License     : MIT

  Slicer is a terminal-first developer tool that parses fixed-length
  messages used by AS400, DB2 middleware, banking switch systems, and
  legacy enterprise TCP APIs.

  It replaces fragile Excel MID() workflows with maintainable,
  spec-driven, version-controlled protocol definitions.


================================================================================
2. PROBLEM STATEMENT
================================================================================

  Enterprise developers debugging fixed-length protocol messages
  currently rely on:

    - manual Excel MID(A1,1,4) substring formulas
    - manual offset arithmetic
    - copy-paste workflows across many spreadsheet cells
    - undocumented per-developer Excel files
    - non-reusable, non-version-controlled parsing logic

  These workflows are:

    - error prone
    - non-shareable
    - non-scriptable
    - slow for onboarding new APIs
    - impossible to grep, diff, or audit


================================================================================
3. SOLUTION OVERVIEW
================================================================================

  Slicer provides:

    - plaintext spec files describing each protocol
    - a generic parser engine that consumes any spec
    - a CLI command `slice` for terminal parsing
    - a helper command `spec` for spec management
    - Neovim keymaps for in-editor parsing
    - JSON / raw / table / offset output modes
    - graceful failure on truncated or malformed input

  Workflow becomes:

    copy raw message  ->  slice  ->  parsed table in 1 second


================================================================================
4. DESIGN GOALS
================================================================================

  - terminal-first workflow
  - human-readable specs
  - minimal typing
  - fast protocol onboarding (under 1 minute)
  - graceful error handling on malformed input
  - Neovim-native integration
  - grep-friendly, git-trackable specs
  - zero configuration files
  - cross-platform (Windows / Linux / Termux)


================================================================================
5. NON-GOALS
================================================================================

  - GUI workflows
  - complex protocol DSL
  - binary / TLV / ASN.1 protocol framework
  - real TCP socket handling (slicer parses strings, not sockets)
  - enterprise configuration boilerplate
  - per-user installers


================================================================================
6. CORE CONCEPTS
================================================================================

  SPEC
    A plaintext file mapping field names to fixed lengths.

  HEADER SPEC
    A single shared spec parsed first for every message. Must
    contain a field named `service_code`.

  BODY SPEC
    A per-service-code spec loaded after the header is parsed.
    File path: specs/body/{service_code}.spec

  DISPATCHER
    Reads header -> extracts service_code -> loads body spec.

  PARSER ENGINE
    Generic sequential offset slicer. Knows nothing about any
    specific protocol.

  PARSED FIELD
    A (name, value, start, end) record produced by the parser.

  PARSE RESULT
    Aggregate of header fields, body fields, warnings, errors,
    service_code, and any unparsed trailing payload.

11. SPEC LANGUAGE
================================================================================

  SYNTAX
    One field per line:

        field_name    length

    Whitespace between name and length is irrelevant.

  COMMENTS
    Lines starting with `#` are ignored.

        # customer header section
        cif       10
        name      30

  BLANK LINES
    Ignored. Use freely to group sections.

  FUTURE TYPE HINTS (planned v0.2)

        amount    13   numeric
        date       8   date:YYYYMMDD
        status     2   enum:OK,KO,PD
        name      30   string:required

  RULES
    - length must be a positive integer
    - field names should be snake_case
    - the header spec MUST contain a field named `service_code`


================================================================================
12. HEADER SPEC
================================================================================

  Location:
    specs/header.spec

  Purpose:
    Shared structure parsed first for every message. Provides the
    `service_code` used to dispatch to the correct body spec.

  Example:

        prefix          4
        channel         8
        service_code    6
        device         20

  Constraint:
    Must contain a field named `service_code`. If missing, the
    dispatcher emits an error and aborts body parsing.


================================================================================
13. BODY SPEC
================================================================================

  Location:
    specs/body/{service_code}.spec

  Purpose:
    Per-API field definitions parsed after the header.

  Example (specs/body/CA1017.spec):

        transaction_id   12
        amount           13
        response_code     2
        customer_name    30

  Lookup Rule:
    service_code = "CA1017"
        -> loads specs/body/CA1017.spec

  Missing Spec Behavior:
    - emit warning
    - keep parsed header fields
    - present remaining payload as `unparsed_tail`


================================================================================
14. DISPATCHER MECHANICS
================================================================================

  Step 1: Read specs/header.spec
  Step 2: Parse header from position 0
  Step 3: Find field named `service_code`
  Step 4: Strip whitespace from its value
  Step 5: Compute body path = specs/body/{service_code}.spec
  Step 6: If exists, parse body from current position
  Step 7: If not, emit warning, store unparsed tail
  Step 8: If trailing bytes remain after body, emit overflow warning


================================================================================
15. PARSER ENGINE
================================================================================

  Pure function. No I/O. No globals.

  Signature:

      sequential_parse(
          message: str,
          fields: list[(name, length)],
          start_pos: int = 0,
      ) -> (parsed_fields, new_pos, errors)

  Algorithm:

      pos = start_pos
      for (name, length) in fields:
          end = pos + length
          if end > len(message):
              emit truncation error
              break
          value = message[pos:end]
          append ParsedField(name, value, pos, end-1)
          pos = end
      return (parsed_fields, pos, errors)

  Properties:
    - deterministic
    - side-effect free
    - trivially testable
    - reusable for both header and body


================================================================================
16. OFFSET CALCULATION
================================================================================

  Offsets are computed automatically. The user never maintains them.

  Example output (--offsets mode):

      OFFSET      FIELD              VALUE
      ----------------------------------------------------
      0-3         prefix             ADSV
      4-9         service_code       CA1017
      10-22       amount             000000000135

  Use cases:
    - protocol debugging
    - spec validation
    - locating malformed bytes
    - diffing two messages by position


================================================================================
17. VALIDATION
================================================================================

  v0.1 (current):
    - field length enforcement (via truncation detection)

  v0.2 (planned):
    - numeric check
    - required / non-empty check
    - date format check
    - enum membership check

  Validation failures emit warnings; parsing continues. The system
  never aborts on a single bad field.


================================================================================
18. ERROR HANDLING
================================================================================

  Slicer never crashes on malformed input.

  CASE 1: Missing header.spec
      -> [ERROR] Missing header.spec at <path>
      -> return empty result

  CASE 2: Missing service_code field in header
      -> [ERROR] header.spec missing 'service_code' field
      -> return header-only result

  CASE 3: Missing body spec
      -> [WARN] Missing body spec: CA7777.spec
      -> show header
      -> show unparsed_tail raw

  CASE 4: Truncated message
      -> [ERROR] Message truncated at field 'X' (need N, have M)
      -> return successfully parsed fields so far

  CASE 5: Overflow (message longer than spec)
      -> [WARN] Extra trailing payload detected (N bytes)
      -> show unparsed_tail

  CASE 6: Invalid spec syntax
      -> ValueError with file:line context

19. CLI INTERFACE
================================================================================

  COMMAND : slice
  PURPOSE : parse one message

      slice                       interactive paste mode
      slice "MESSAGE"             positional argument
      cat msg.txt | slice         stdin pipe
      Get-Content msg.txt | slice (PowerShell pipe)

  OPTIONS:
      --json        JSON output
      --raw         key=value output
      --offsets     include offset column

  COMMAND : spec
  PURPOSE : manage spec files

      spec list                   list all body specs
      spec show CA1017            print contents of a spec
      spec create CA2020          paste table -> write spec file

21. NEOVIM INTEGRATION
================================================================================

  PRINCIPLE
    All business logic lives in the Python CLI. The Lua plugin is
    only a thin wrapper that shells out to `slice`.

  KEYMAPS
    <leader>sp    slice current line
    <leader>ss    slice visual selection
    <leader>so    open spec matching CA#### on current line

  OUTPUT BUFFER
    Opens in a right vertical split with:
        buftype    = nofile
        bufhidden  = wipe
        swapfile   = false
        modifiable = false
        filetype   = slicer-output

  REQUIRED ENV VAR (for <leader>so):
    SLICER_HOME  =  path to slicer project root

23. NEW API ONBOARDING
================================================================================

  Step 1: Receive protocol doc (Excel / Word / email / plaintext).
  Step 2: Run:

      spec create CA2020

  Step 3: Paste FIELD LENGTH lines.
  Step 4: End input with Ctrl-Z + Enter.
  Step 5: File created at specs/body/CA2020.spec
  Step 6: Commit to git:

      git add specs/body/CA2020.spec
      git commit -m "spec: add CA2020 onboarding"
      git push

  Total time: under 1 minute.


================================================================================
24. BATCH PROCESSING
================================================================================

  Parse many messages from a log dump:

      Get-Content db2_dump.txt |
          ForEach-Object { $_ | slice --raw }

  Find which messages lack body specs:

      Get-Content all_messages.txt |
          ForEach-Object { $_ | slice --json } |
          Select-String "Missing body spec"

  Diff two parsed messages:

      slice "MSG1" --raw > a.txt
      slice "MSG2" --raw > b.txt
      git diff --no-index a.txt b.txt

27. GLOSSARY
================================================================================

  SPEC                a plaintext file mapping field name -> length
  HEADER              the shared front portion of every message
  BODY                the API-specific tail portion of a message
  SERVICE CODE        the identifier (e.g. CA1017) selecting a body spec
  PARSED FIELD        one (name, value, start, end) tuple
  PARSE RESULT        full record: header + body + warnings + errors
  DISPATCHER          the module that selects which body spec to load
  UNPARSED TAIL       bytes left over after parsing finishes
  TRUNCATION          message shorter than the spec requires
  OVERFLOW            message longer than the spec consumes

29. PHILOSOPHY
================================================================================

  Slicer is not a generic parser framework.

  It is a developer-first protocol inspection tool optimized for:

    - enterprise fixed-length messages
    - AS400 / DB2 environments
    - terminal-first debugging
    - rapid protocol onboarding
    - middleware troubleshooting

  Guiding principles:

    - human-first specs
    - minimal friction
    - graceful failures
    - fast parsing
    - terminal-native UX
    - editor integration
    - spec-driven architecture
    - reusable parser engine
    - everything plaintext, everything git-trackable

  Primary focus:
    developer productivity and protocol visibility.
